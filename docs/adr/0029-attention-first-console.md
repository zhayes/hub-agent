# ADR 0029：注意力优先的控制台，且 Web 是唯一的人类任务入口

- **状态：** 已接受（Accepted）
- **日期：** 2026-11-27
- **相关：** PRD §5（FR-CLI-01）、§9.1、§9.2、§10.1、§2.1-11；ADR 0016 / 0019 / 0020 / 0022 / 0026；`docs/PLAN-CONSOLE-INTERACTION.md`；`docs/UI-SPEC.md`
- **证据：** `packages/web/src/app/AppLayout.tsx`（5 个平级目的地 + 注意力分散 4 处）、`app/store.tsx`（SSE 不触发重取）、`features/chat/ChatView.tsx`（澄清只在线程内可见）、`shared/api.ts`（`chatApi.create` 仅接受 worktree/title/permissionMode）、`interfaces/cli/cli.ts`（`run` 的 `--agents` / `--verify-command` / `--delivery` / `--detach`）

---

## 1. 背景

### 1.1 现在的控制台是状态陈列柜

五个平级目的地（对话 / 任务 / Agent 现场 / Agent 接入 / 审批）+ 设置，判据是"系统有哪些实体"，不是"用户此刻要做什么"。三个具体后果：

1. **注意力分散在四处**：app bar 文案（`<860px` 被隐藏）、rail 徽标（只管审批）、任务详情内横幅、会话内授权卡。
2. **澄清不可发现**：`clarification` 只作为线程内的消息卡渲染；线程进入 `waiting` 后，从任务页和审批页都看不见。
3. **"live" 名不副实**：SSE 事件只追加进 30 条列表，不触发任务/审批重取，数据停在打开页面那一刻。

### 1.2 任务不一定有会话，这是"待办无法归位"的根因

CLI 可以直接创建任务（`ha run`），使 `task ↔ thread` 成为 0..1。于是一条待审批可能没有会话外壳，任何"把待办挂在会话列表上"的方案都必须伪造容器——即把运行伪装成对话，与 ADR 0022 的初衷相反。

### 1.3 用户要的是三件事

`US-001` 说一句要干什么、`US-006` 该我出手时立刻知道、`US-007/008` 完成后能判断该不该信。这三件事都不是"浏览实体"。

---

## 2. 决策

### 2.1 Web 是唯一的人类任务入口

- **人**只有一条建任务路径：控制台的对话输入（`POST /api/v1/chat/threads/:id/messages`，Brain 决定 reply 还是建 Task）。
- **CLI 不提供任务创建**：`ha run` / `hubagent run` 的创建语义取消，默认拒绝执行真实派单。
- **CLI 保留**（它们不创建任务）：
  - 只读视图：`task list|show|events|evidence|decisions`；
  - 恢复动作：`task retry|answer|pause|resume|cancel|clean`；
  - 审批：`approval list|approve|reject`；
  - 运维：`doctor / init / config / logs / gc / maintenance`；
  - Agent 接入：`agent add|scan|adopt|login|verify|list|show`。
- **唯一例外**：显式 `--allow-task-create`（或等价测试开关），仅用于诊断与回归。理由是 M4–M10 的验收、`test:brain-real`、`test:srt-acp`、真实 harness 复核全部依赖它；删干净会失去"Pi 模型 + 真 harness 端到端"的唯一抓手。默认关闭，不得在文档里作为常规用法出现。
- **内部 API 不受限**：`bench/run.ts` 直连 `runGoalWithBrain`，不属于 CLI 入口。

这条决策**推翻**了两处既有口径，在此显式记录：

| 位置 | 原文 | 现状 |
|---|---|---|
| PRD §2.1-11 / V1.2 修订点 ③ | 「可解释性由 CLI + 只读端点兑现，**Web Console 不再是前置条件**」 | 可解释性仍可由 CLI 兑现；但**开工**以控制台为前置条件。二者必须分开表述 |
| PRD FR-CLI-01 | 「任务创建、状态与只读视图」 | 降级为「任务查看与恢复（不创建）」 |

### 2.2 注意力优先的信息架构

- **导航收敛为 2 个目的地 + 设置**：对话（`/`、`/chat/:id`）、Agent（`/agents`：现场 / 接入 分段）、设置。
- **运行是对象，不是地点**：`/tasks/:id` 保留、可深链、可书签，但不占导航位。运行列表是"运行"这一状态的筛选视图，不是必须巡的页面。
- **收件箱不占导航位**：一个常驻指示器（app bar，"轮到你 N"，窄屏不隐藏）+ 紧凑浮层队列。判据是「系统已停下等人做决定，而人还没做」；运行中的工作、通知历史、无决定的完成项都不进。
- **澄清归会话**：线程列表按 `status = waiting` 打标记并置顶；线程内就地作答。
- **审批与失败归运行**：运行页对应节点内联处理，会话里对应的回合卡保留（现状即如此），完整证据在运行页。

### 2.3 单主操作与"能就地处理完"

队列里每条只有一个实心动作，卡片必须回答：谁在等 / 精确要执行什么 / 为什么有风险 / 影响范围 / 不做会怎样。就地能处理完，不是跳转清单。

### 2.4 Web 必须接管 CLI 的既有能力（硬门禁）

禁止 CLI 建任务，等于把这些能力收归控制台；不做就是功能下线。`chatApi.create` 目前只接受 `worktree / title / permissionMode`，以下**四项**必须在此之前补齐：

| 能力 | 今天的唯一入口 | 缺失后果 | 现状（2026-11-28） |
|---|---|---|---|
| 并行多 Agent 扇出（US-003） | `ha run --agents a,b` | 并行协作不可用 | ✅ 会话运行设置的「可用 Agent」 |
| 验收命令 | `ha run --verify-command` | 用户无法定义"什么算通过"，直接打在"可验收"上 | ✅ 会话运行设置的「验收命令」 |
| 交付策略（PRD §6.12.4） | `ha run --delivery` | 交付模式不可选 | ✅ 任务页「导出补丁」+ 自动化路径的 `branch-only` |
| 后台执行 | `ha run --detach` | 长任务必须页面常开 | ✅ `ChatService.start` 的 `void this.run(...)` |

~~预算上限（`budget` 为契约必填）~~ —— **已移出门禁**（ADR 0031）：运行时没有用量与费用计量，`maxTokens` / `maxCostUsd` 无法执行，已从契约删除；保留的是不可配置的墙钟与回合护栏。

**门禁状态：四项已可用。** 由此“先补 Web、再关 CLI”的技术前提已成立；但 `ha run` 本体尚未真正关闭（没有 `--allow-task-create` 开关，见 ADR 0031 §5），关闭入口是独立的一轮工作。

### 2.5 A2A 入站委托不属于"人类入口"

远程 Peer 委托创建任务（ADR 0026）是机器入口，按独立口径另行定义；本条只约束人。P1 落地时必须在此补一节。

## 3. 被否方案

- **收件箱做第 5 个导航目的地。** 于是又变成"必须记得去那里"的表面——正是本次要消除的病症。队列常态长度在个人本地场景很短（现有 51 个基线任务全是单子任务），页面是过度结构；浮层足够，且升级门槛可测（常态 >8 条或需要分组/批量）。
- **把审批也全部塞进对话列表。** 在 2.1 之后技术上可行（每个 task 都有 thread），但会话列表会同时承担"导航"和"排水"两种相反动作：批准后条目消失导致列表在手底下重排，导航失去位置感。且审批的证据束与对话不同构，塞进去就是详情页穿着聊天的衣服。
- **独立 Dashboard（PRD §9.2 页面一）。** KPI 看板与 UI-SPEC §1「Chrome 安静，数据发声」冲突，且成本统计是 P1（FR-COST-02）。本期不做，能力落点见 §4 映射。
- **保留 CLI 作为并列入口。** 双入口使 `task ↔ thread` 恒为 0..1，注意力无法收敛到一处；这正是 1.2 的根因。
- **禁止 CLI 建任务并直接删掉 `run`。** 会让 M4–M10 的验收命令、真实 harness 复核全部失去抓手，等于用"入口收敛"换掉"可验证性"。

---

## 4. 后果

**正面**

- `task ↔ thread` 从 0..1 变为 1..1：每条审批、每次失败都有会话外壳，注意力可以真正收敛。
- 澄清、审批、失败第一次有单一可信入口；窄屏不再丢失提示。
- 运行页从"第 5 个目的地"变成可链接的对象，深链与书签语义清晰。

**负面 / 必须承担**

- **网页开不了就无法开工。** 缓解：`/chat` 是 2D 页面，不依赖 WebGL（UI-SPEC §11.4 的 CLI 回退只覆盖 Agent 管理，不受影响）；daemon 未启动时要给出唯一可执行动作，而不是死路。
- 脚本化/CI 用法改为调用本地 HTTP API，而不是 `ha run`。
- 需要在 Web 侧新增五项能力（2.4），本期工作量顺延，不是白捡。
- PRD §9.2 的 7 个"页面"需重新理解为能力清单，落点如下：

| PRD 页面 | 新落点 |
|---|---|
| 页面零 Chat | 目的地「对话」 |
| 页面一 Dashboard | 不做看板；运行状态进常驻指示器 + 运行列表 |
| 页面二 Task Center | 运行索引 + 运行详情（对象，非目的地） |
| 页面三/四 Agent Center / Detail | 目的地「Agent」（现场 / 接入 分段） |
| 页面五 Approval Center | 收件箱浮层 + 线程/运行内联 |
| 页面六 Network | 未实现（A2A，P1/P2），届时另行定义 |
| 页面七 Settings | 目的地「设置」 |

---

## 5. 复审触发条件

- A2A 入站委托上线（需补 2.5 的口径）。
- 出现合法的脚本化批量建任务需求（重新评估“双入口”的代价是否可接受）。
- 收件箱常态 >8 条，或需要按仓库分组、多选批量（此时浮层升级为页面）。
- 真实使用数据显示“批处理/无人值守”是主要形态，而非“人盯着决定”。

## 6. 复审 / 变更（2026-11-27，P1 设计轮）

**结论未变**，本节只补充渲染证据与一条待定项。证据在 `docs/design/`（不入库）：现状 36 张基线 + 24 份 `tells`，三个壳层/组件候选的明暗 × 1440/768/390 渲染稿。

1. **§2.2「收件箱不占导航位」获得证据支持。** 常驻式方案（无 rail、右侧 340px 注意力栏）已渲并否定：该宽度只给到 316px 内宽，`git push origin fix/auth-redirect-loop` 被横向裁切——而 §2.3 要求卡片必须给出“精确要执行什么”。此外它常驻占去画布 24%，空态是一块付费的空白，手机端两栏全隐导致注意力彻底消失。浮层 440px 可同时容纳命令、影响面与拒绝后果。
2. **新增实现判据（来自渲染）：** 决策卡里的命令必须换行，不得横向裁切或省略；一旦裁切，卡片就不再回答“要执行什么”。
3. **新增：一个组件，三种容器。** 决策卡在浮层（360 密集）/ 会话（520）/ 运行页（720，多一行 `Verified`）使用同一顺序与同一主操作规则，不做第二套组件。
4. **56px rail 已定：取消（2026-11-27 第二张对比稿后）。** 对比了「页签进 app bar」（D）与「页签 + 手机底部条」（E）：D 在 1440 更好（省 56px、页头与正文同列），但 ≤860 时丢了底部导航、注意力胶囊被挤成两行；E 取其桌面优点并保留拇指区，且底部条**带文字标签**（比原图标 rail 只能靠 tooltip 更好读）。结论：≥861 页签，≤860 带标签底部条，rail 取消。代价：手机端注意力控件只显计数，语义靠 `aria-label` 与浮层标题补。
5. **现状证据补充（不改结论）：** 注意力实际分散在**五处**（含 `/agents` 底部横幅），不是四处；澄清只有在 `waiting` 线程的详情头部才有胶囊，列表行本身无标记；会话页权限下拉是原生 `select`（142×27）；英文界面会出现 `6分0秒` 与 `request_human` 这类内部枚举。
6. **方向注记：** `/agents` 的 HUD（点 + 文字状态、底部花名册、注意力横幅）是全站表达最好的一面，新体系应沿用这套语言而不是另造一套。
7. **会话历史的落点（评审时补）。** 取消 rail 后，E 稿最初**没有历史入口**，只剩当前一条对话——这是稿子的缺陷，不是设计决定。现定：**当前对话标题即切换器**（带 chevron），点开左侧抽屉：搜索 + 历史列表（行内带状态与 `2 need you`）+ New conversation；⌘K 直达。不把快捷键当唯一入口：历史必须可见、可点。
8. **已知工艺缺陷（待 P2 修）：** 18% 遮罩压不住饱和度高的元素——窄屏下抽屉/浮层只盖住部分画布时，顶栏的强调色胶囊看起来仍是“活的”。二选一：窄屏遮罩加深，或让顶栏在模态打开时降权（pointer-events + 透明度）。

## 7. 复审 / 变更（2026-11-28，三栏外壳）

**§2.2 的导航拓扑被 ADR 0032 取代，其余结论保留。** 具体变更：

| 本条原文 | 现状 |
|---|---|
| 导航收敛为 2 个目的地 + 设置，会话历史进抽屉 | 左栏常驻：新建工作区 / Agent 活动 / 注意力 / 按目录分组的会话 / 设置；不再是“目的地页签 + 抽屉” |
| 运行是对象，不占导航位（保留） | 不变；但 `/tasks/:id` 打开的是右栏详情，不是整页（不离开对话） |
| 收件箱不占导航位（保留） | 不变；指示器从顶栏胶囊移到左栏一行，仍无待办时不出现 |
| §6.4 rail 取消 | 左栏重新常驻，但内容不是目的地而是**工作区与会话**（ADR 0032 §3 否掉的仍是图标 rail） |
| 设置是目的地 | 设置成为可深链的弹框，Agent 接入并入其中 |

本 ADR 的 §2.1（Web 是唯一的人类任务入口）、§2.3（单主操作、就地处理完）与 §2.4（Web 接管 CLI 能力）不受影响。
